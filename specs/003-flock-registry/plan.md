# Implementation Plan: Flock Registry

**Branch**: `003-flock-registry` | **Date**: 2026-03-16 | **Spec**: [spec.md](spec.md)

## Summary

Extend the existing poultry module to fully implement the Flock Registry as specified. The existing `Flock` entity, `FlockService`, `FlockController`, and all frontend components exist but are incomplete: they are missing batch codes, expanded purpose/status enums, age calculation, housing location assignment, and the mortality/cull event system. A new `HousingLocation` entity is needed (no existing equivalent for poultry). The `mortality_records` table exists in the DB but has no Java layer yet.

## Technical Context

**Language/Version**: Java 21 LTS (authoritative for active feature; allowed range: Java 17/25), TypeScript strict (frontend)
**Primary Dependencies**: Spring Boot 3.4.x (authoritative), Vue 3 (Composition API), Pinia, Tailwind CSS 4
**Storage**: PostgreSQL 15 via Flyway migrations (next migration: V19)
**Testing**: JUnit 5 + Mockito (backend unit), Vitest (frontend unit), Playwright (E2E)
**Target Platform**: Linux server (backend), PWA in modern browsers (frontend)
**Project Type**: Monorepo web application (Spring Boot API + Vue 3 PWA)
**Performance Goals**: Flock list load ≤ 2s for 20 concurrent flocks; headcount update reflected in same session
**Constraints**: Offline-first (PouchDB queue for writes), multilingual FR/AR/Darija with RTL
**Scale/Scope**: Single-user farm operators; dozens of concurrent flocks per account

## Implementation Phases

### Phase A — Database Migration

**File**: `V19__flock_registry_enhancements.sql`

1. Create `housing_locations` table
2. Add `housing_location_id UUID REFERENCES housing_locations(id) ON DELETE SET NULL` to `flocks`
3. Add `batch_code VARCHAR(100) NOT NULL DEFAULT ''` to `flocks`
4. Add `UNIQUE INDEX uq_flock_batch_code(user_id, batch_code) WHERE batch_code <> ''`
5. Add `type VARCHAR(20) NOT NULL DEFAULT 'NATURAL_DEATH'` to `mortality_records`

---

### Phase B — Backend: New Entities and Enums

**Order matters** (enum changes before entity changes):

1. Extend `FlockPurpose`: add `DUAL_PURPOSE`, `BREEDERS`
2. Extend `FlockStatus`: add `PHASED_OUT`
3. Create `HousingLocationType`, `MortalityType`, `MortalityCause` enums
4. Create `HousingLocation` entity (mapped to `housing_locations`)
5. Create `MortalityRecord` entity (mapped to `mortality_records`)
6. Modify `Flock` entity: add `batchCode` field and `housingLocation` ManyToOne FK

---

### Phase C — Backend: Repositories

1. `HousingLocationRepository` — `findByUser(User)`, `findByUserAndLocationType(User, HousingLocationType)`, `countByUserAndId(User, UUID)` (ownership check)
2. `MortalityRecordRepository` — `findByFlockOrderByMortalityDateDesc(Flock)`, `findByFlockAndUser(UUID flockId, UUID userId)`

---

### Phase D — Backend: DTOs

All Java records. Follow Records Mandate.

1. Modify `CreateFlockRequest`: add `@NotBlank @Size(max=100) String batchCode`, `UUID housingLocationId`
2. Modify `UpdateFlockRequest`: add `UUID housingLocationId` (no batchCode — read-only)
3. Modify `FlockResponse`: add `String batchCode`, `UUID housingLocationId`, `String housingLocationName`, `Integer ageWeeks` — computed in `from()` factory
4. Create `CreateHousingLocationRequest`, `UpdateHousingLocationRequest`, `HousingLocationResponse`
5. Create `CreateMortalityEventRequest`, `MortalityEventResponse`

---

### Phase E — Backend: Services

**HousingLocationService**:
- `findAll(User, HousingLocationType)` — optional type filter
- `findById(User, UUID)` — ownership check
- `create(User, CreateHousingLocationRequest)` → `HousingLocationResponse`
- `update(User, UUID, UpdateHousingLocationRequest)` → `HousingLocationResponse`
- `delete(User, UUID)` — check no ACTIVE flocks assigned; throw 409 if blocked
- `currentFlockCount(UUID locationId)` — derived field for response

**FlockService** (modifications):
- `create()`: validate batch code uniqueness per user (query `findByUserAndBatchCode`); lookup `HousingLocation` by `housingLocationId` if provided
- `update()`: support `housingLocationId` change
- `delete()`: set status to `PHASED_OUT` (not `FINISHED`)
- `FlockResponse.from()` factory: compute `ageWeeks = ChronoUnit.WEEKS.between(flock.startDate, LocalDate.now())` — null if startDate null

**MortalityService**:
- `findByFlock(User, UUID flockId)` → `List<MortalityEventResponse>`
- `create(User, UUID flockId, CreateMortalityEventRequest)`:
  1. Load flock (ownership check)
  2. Validate flock is ACTIVE
  3. Validate `event.count <= flock.currentBirdCount`
  4. Persist `MortalityRecord`
  5. Decrement `flock.currentBirdCount` by `event.count`
  6. Save flock
  7. Return `MortalityEventResponse` with `updatedFlockHeadcount`
  — All steps in a single `@Transactional` method

---

### Phase F — Backend: Controllers

**HousingLocationController** (`/api/v1/housing-locations`):
- `GET /` — list, optional `?type=` filter
- `POST /` — create
- `GET /{id}` — get one
- `PUT /{id}` — update
- `DELETE /{id}` — delete (409 if active flocks)

**MortalityController** (`/api/v1/flocks/{flockId}/mortality-events`):
- `GET /` — list events
- `POST /` — create event

**FlockController** (modifications):
- Update `status` param to accept `PHASED_OUT`
- Update `purpose` param to accept `DUAL_PURPOSE`, `BREEDERS`
